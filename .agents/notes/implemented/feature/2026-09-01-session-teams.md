# Conversation directory and role-window teams

English | [中文](2026-09-01-session-teams.zh.md)

## Summary

`@vibeinging/dsh-session-teams` gives every ordinary DSH conversation visible to one Host a direct title-based route. The Host resumes cold targets on send, and one direct user request can create several named top-level role windows led through durable task state, dependencies, and bounded retry.

The implementation has no connection graph, invitation grant, or disconnect operation. A conversation remains addressable while it remains in DSH persistence. Natural-language requests to stop talking to one window are handled by the model's ordinary conversation context.

## Decisions

The official `SessionPersistence` service is the durable directory. Revision-aware inspection folds `session/title` and `request/context`; the live `AgentRegistry` overlays current activity. Routing includes every top-level session visible to the Host, exact duplicate titles reject, and one unreadable persisted session is skipped without blocking application startup or the rest of the directory.

`send_window_message` accepts a display title or an optional exact link. Cold targets resume through `SessionController.resolveAgent()`, which restores their normal preset, tools, system prompt, permissions, and selected model instead of constructing a bare Agent. Model-authored messages are durable `user/message` events with a user-shaped source, so standard Chat shows a normal bubble attributed to the sending window; a registered non-user kind was tried and rolled back because the official Chat folds injected-context nodes into its collapsed turn-process region. Task-less relay text carries a fixed reply contract instructing the receiving model to answer through `send_window_message` without `target_name`, mirroring the assignment contract that team members already follow; the parser strips the contract and the client card hides it. Direct-human authorization applies the official human-source rule: a user-kind source counts as a human request only when its fields stay within the official vocabulary of `kind`, the browser prompt correlation `rpcId`, and the Host-validated `clientTimeZone`, excluding this plugin's relays and every other producer's metadata-carrying user-shaped messages; malformed claims also fail closed. A working target receives `steer()` delivery at its nearest step and an idle target starts a turn. Scheduled team tasks use `followup()` for a distinct task turn, and the model decides whether another message helps without a reply counter. Ordinary replies use the newest relay in the current turn, while a final task result uses the newest trusted task assignment in durable member history and therefore survives later reminders and turns. The leader's current team state still validates the team, task, owner, and status before accepting the result.

`create_window_team` accepts the compatible one-task shorthand or the complete per-member `tasks` graph, then validates all ids, cross-member dependencies, limits, and acyclicity before side effects. A unique existing exact-title conversation is reused; multiple exact matches reject before any member changes. Only missing members are provisioned. The optional ProductHost reports whether the initiating Session is product-bound or DSH-only. A product-bound leader asks the parent to create the App Session and project binding; a DSH-only leader calls `SessionController.create()` directly. Both paths use `selectModel()` and `resolveAgent()`, so the official preset owns the complete tool and prompt composition while the leader's exact active provider, model, and explicit reasoning effort are selected through the controller. An older ProductHost without the scope query remains product-authoritative, and errors never trigger a different creation path. A failed member returns a failure or `partial` result without deleting normal persisted conversations. When a leader Session resumes, idempotent Workspace attachment repairs any known team member missing from the leader's Workspace.

Complete log-only records using the official `team/task` shape in the leader Session are authoritative for team tasks. A plugin-namespaced selector keeps the record outside the implicit Agent Team rooted at that Session. Each new state appends a higher revision without entering or replacing the model-visible surface, so it does not increment `replaceGeneration` or begin a new request series. The official Session Projection carries the same rebuildable state to the browser; a state-version change discards only an incompatible derived checkpoint and refolds the durable log. The fold accepts earlier plugin-source `snapshot` messages and `window-team/state` values without rewriting them. This avoids both an out-of-repository Session event type that the official persistence catalog cannot recognize after restart and a second database. The scheduler claims only dependency-ready work. Technical failures may retry within the configured bound; work failures remain for leader judgment. Manual reassignment moves only unstarted, waiting, or failed work and does not duplicate running or completed work.

The browser reads `useSessions`, `useInput`, `inputActions`, and `useProjection('windowTeam')`. With a team it shows the goal, progress, members, roles, and task states before an expandable list of other ordinary conversations. Without a team it shows the full addressable directory. Selecting another conversation prefixes the existing draft with its displayed title through `InputActions.setDraft()`, closes the panel, and restores composer focus; the user still submits an ordinary message for model-directed routing. The panel has no invitation, connect, disconnect, or removal control. Trusted relays shadow Chat's `user` and `steering` cells with a presentation wrapper: unrelated messages keep the shipped renderer, while a valid relay gets a compact source header whose exact Session Controller action opens the sending conversation. A Slot declaration becomes observable before every waiting injector has registered its entry, so the wrapper subscribes to the Chat node Slot and installs only after both shipped message renderers exist. These client-only projections do not mutate the durable event or model surface.

The package and loader are named `dsh-session-teams` and `session-teams`; visible copy remains **Window collaboration**. New relays use the session-teams package identity and envelope, while the parser accepts the legacy window-link identity and envelope from durable Session history.

## Verification contract

Focused tests cover durable directory filtering and caching, Session Controller cold resume, complete preset provisioning without a hardcoded tool list, exact active model selection, product-bound creation, DSH-only creation under a present ProductHost, invalid scope rejection, duplicate-title refusal, direct sends without prior state, composer target insertion, navigable relay cards, built-in rendering fallback, absent-source presentation, fail-closed human authorization, model-directed replies, task assignments that survive ordinary reminders and later turns, member lookup of leader-owned team state, team results through the normal message tool, compatible one-task creation, an atomic cross-member task graph, unique exact-title reuse, ambiguous-title rejection before side effects, Workspace attachment, dependency release, technical delivery retry, manual reassignment, official Host inbox delivery, official projection composition, log-only team-state replay, stable model-surface generation, earlier snapshot compatibility, the team-first browser panel, protocol parsing, and duplicate suppression.

The release gate must also prove the built Host and client artifacts, package contents, and real DSH Desktop flows: send by title after a full restart with no connection step; create dependent Development and Testing windows in the leader's Workspace; and reuse two existing named windows while one atomic graph alternates ten dependent tasks to completion. Acceptance must confirm that the leader panel follows task state and that log-only mutations do not replace the model surface or split the request series.

## Boundaries

The plugin does not queue while the Host is stopped, route across Hosts, copy transcripts, infer completion from ordinary text, reassign automatically, or delete conversations. Queue acceptance is not task completion; a member marks the final `send_window_message` with `task_outcome`, and the newest trusted assignment in its durable history supplies the task id.
